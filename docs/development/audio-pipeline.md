# Capture and recognition lifecycle

`SpeechEngine` owns capture and native recognition. Original bounded 16 kHz mono PCM is authoritative, retained independently of decoder input and saved for successful History. Never silently drop samples, mutate saved PCM, auto-submit a transcript or infer recognition accuracy from complete range coverage. Capture queues must hold the full capture cap so slow inference cannot block the microphone. Retain ownership until in-flight recorder reads and native operations have drained; an active JNI call may not be interruptible.

## Streaming and stop

For Nemotron, use one online stream for a whole live session or saved file. Feed all PCM, pauses included, in 200 ms blocks on a separate worker; snapshot the active model per session. Flush a shorter final block without waiting for it to fill. The feed block size is distinct from the model's chunk size. When explicitly enabled, local dictation may display interim hypotheses in its separate two-line overlay. Remote PCM can also deliver replaceable unvalidated PARTIAL IPC previews to its owner; local live and file IPC cannot. At Stop snapshot final text settings, drain backlog, feed finalization silence separately from saved PCM, signal `inputFinished`, drain ready frames and return one final result without a second full-file decode. InputFinished alone cannot necessarily flush incomplete NeMo encoder chunks. Cancel skips finalization and result but waits for native ownership to be safely released. A slow device can make Stop wait for backlog; no latency or quality guarantee follows from host checks.

For Nemotron, remote PCM uses the same online worker, without AudioRecord. An IO reader preserves
raw samples and sends bounded blocks; it accepts at most five minutes and handles
split 16-bit samples. It waits for both owner FINISH and pipe EOF, validates the
independent count and SHA-256, then releases the final short block and permits decoder
flush. Failed or cancelled input is never saved in History or published as a result;
earlier previews are unvalidated and must not be persisted or submitted. A bounded
nonblocking pipe poll and descriptor closure allow cancellation while a writer stalls.

ML Kit GenAI Speech Recognition Advanced is an alternative, device-dependent engine; do not silently substitute Basic. Verify its current status before inference and keep its recognizer, input and cancellation ownership scoped to the current session. The app currently uses one-shot input and does not implement ML Kit streaming preview, even though the SDK supports streaming; it waits until recording stops and uses the same original PCM and final result pipeline. The selected speech locale is explicit; it does not imply automatic language detection. ML Kit model management belongs to the platform, not the Nemotron downloader.

Fluid Speech Pro uses sherpa's offline NeMo transducer, with the original PCM also used for History. It supports completed files and validated remote PCM but not acoustic vocabulary bias. The shared streaming-preview setting enables local Fluid CPU/NPU provisional previews; remote PCM sends provisional PARTIAL events independently of that local overlay setting. A separate worker re-decodes the active window after VAD pauses or at two-second intervals during speech, commits a segment at a qualifying pause in its last 40% or at its hard limit, and coalesces stale work. These are replaceable offline hypotheses, not a stateful streaming decoder; they are never inserted or saved as the final result. Microphone capture and remote PCM reception do not wait on inference. Stop drains active native work and runs the existing full offline final pass; Cancel suppresses results. Remote final output additionally requires EOF and matching FINISH count and SHA-256. Each session retains its originally selected model. The model card reports tests on clips up to 30 seconds. Final CPU audio is decoded in contiguous chunks of at most 30 seconds; the bundled Silero V4 VAD proposes a pause in the final 40% of each window, with a forced split at the limit if none qualifies. VAD selects boundaries only: no final-pass samples are trimmed or discarded. If VAD fails, fixed-size chunks are used.

The experimental SM8750 QNN variant is a separate offline model selection with the same VAD boundary policy but a 10-second hard chunk limit and no silent CPU fallback. Both variants can misrecognize speech at forced boundaries or lose decoder context at any boundary; VAD can also misclassify quiet speech. A live, separate VAD worker drives the local stop square (red=speech, gray=silence, white=unavailable) without blocking capture. The CPU VAD remains separate from QNN inference; its pinned 16 kHz, 512-sample Silero V4 asset uses 0.50 onset, 0.35 exit, 64 ms onset and 300 ms pause thresholds. Inference and indicator behavior require Android device validation.

### Fluid stateful buffered TDT: feasibility and outstanding backend

NVIDIA-style buffered TDT streaming is **not implemented**. The optional Fluid live preview repeatedly recognizes bounded independent windows and is not equivalent. Preserve original PCM independently for the offline final pass and History.

The focused feasibility investigation established these concrete boundaries:

- **Packaged Java and C++ APIs:** `javap` on the actual sherpa-onnx 2.0.1 AAR shows that `OfflineStream` offers waveform input/options/release, not features or predictor state. The exported `sherpa_onnx::cxx::OfflineRecognizer`/`OfflineStream` symbols are likewise whole-stream wrappers; they do not export the internal `RunEncoder`, `RunDecoder` or `GetFrames` operations. Switching from Java to the packaged C++ wrapper therefore does not supply the missing decoder API. `OnlineRecognizer` requires differently exported streaming graphs.
- **Direct Android ONNX Runtime is not a dependency-only fix:** Maven Central provides `com.microsoft.onnxruntime:onnxruntime-android:1.28.0`, containing Java bindings, `libonnxruntime4j_jni.so`, `libonnxruntime.so`, and C/C++ headers. Inspection of the actual ARM64 ELF dynamic symbols/version requirements shows its JNI library requires `OrtGetApiBase@VERS_1.28.0` and two provider functions at that version. Sherpa's JNI/C API libraries require `VERS_1.28.2`; its bundled runtime exports those functions at `VERS_1.28.2`, not `VERS_1.28.0`. The Maven runtime exports only `VERS_1.28.0` for those functions. A Gradle `pickFirst` for either runtime leaves the other binding with an unsatisfied ELF symbol-version requirement; shared C API compatibility alone does not resolve it. Maven metadata lists no Android 1.28.2 artifact. No mismatched dependency or blind packaging workaround was added.
- **Practical native route:** an app-owned JNI bridge compiled against sherpa's exact runtime (using its C API via `OrtGetApiBase`, with matching headers/API selection), or matching upstream-built sherpa/ORT-Java artifacts, can make direct graph inference possible without modifying third-party sources. The inspected SDK has no installed NDK and this project has no existing CMake/native integration. That toolchain and bridge must be established before native compilation can verify this route; no installation or native rebuild was attempted. Binary-rewriting third-party ELF version tables is not an acceptable substitute.
- **The existing Fluid graphs do expose the required math:** pinned encoder metadata declares 128 input features, per-feature normalization and 8× subsampling. Encoder inputs are float `[B,128,T]` and int64 lengths; outputs are float `[B,1024,Tenc]` and int64 lengths. Predictor inputs are int32 tokens/lengths and two float `[2,1,640]` recurrent states; its exported state names include `states.1` and `onnx::Slice_3`. The joiner emits 8198 logits: 8192 vocabulary tokens, blank ID 8192, then five duration classes (0–4). Implementations must validate these exact graph contracts rather than assuming generic tensor names or int64 token inputs.
- **Frontend is outside these graphs:** supply 128-bin Slaney mel power features with 16 kHz audio, 512-point FFT, 400-sample symmetric Hann window, 160-sample hop, 0.97 pre-emphasis, additive log guard `2^-24`, and per-feature sample-standard-deviation normalization (`sqrt(var) + 1e-5`). The [onnx-asr NeMo frontend](https://github.com/istupakov/onnx-asr/blob/main/preprocessors/nemo.py) provides an existing reference, including ONNX-exportable STFT and convolution variants; its packaged preprocessor is not included in this app or the sherpa AAR. Window padding, frame count and normalization domain must be matched and checked; merely setting `FeatureConfig.featureDim = 128` does not expose features to a direct ORT decoder.
- **Required stateful algorithm:** follow [NVIDIA's chunked inference approach](https://github.com/NVIDIA/NeMo/pull/9106): recompute the bounded left+chunk+right encoder context, trim to the exact central encoder-frame range, and append by carrying predictor output/recurrent state and TDT duration overshoot into the next chunk. Context starts/chunk sizes must align with the 8× subsampling grid (80 ms); never decode left/right context twice. Handle zero-duration emissions with a bounded token loop, blank+zero duration progress, final short chunks and Stop flush. Keep one model owner under the native lifecycle lock; do not retain duplicate Fluid weight sessions for streaming and the final offline pass.
- **VAD is not a streaming backend:** the bundled pinned Silero V4 model now provides boundary hints and a local live indicator for offline Fluid recognition. It does not provide the predictor state, streaming context, or VAD/preroll/flush path required for Fluid streaming. VAD false negatives must never remove audio from the final offline pass or History. An RMS/energy gate must not be presented as a trained VAD.

This is feasible as a dedicated backend integration, but not confidently implementable as a minimal Java dependency change with the current prebuilt artifacts/toolchain. Expect several developer-days for the native/runtime prerequisite, frontend/decoder parity, VAD provisioning and lifecycle integration, plus separately authorized device validation/tuning. The fastest currently working streaming alternative is the existing Nemotron engine. Keeping Fluid offline is the safe alternative until its direct backend is ready. Verification comprised artifact/ELF/API and graph inspection, plus a host-only ONNX Runtime 1.31.0 CPU predictor/joiner smoke run with the pinned real weights: predictor output `[1,640,1]`, both recurrent states `[2,1,640]`, and finite joiner output `[1,1,1,8198]`. This did not verify a frontend, streaming decoder, speech accuracy, Android native loading or device behavior. No app build or installation was performed.

ML Kit diagnostics retain at most 40 sanitized status, phase, known exception type and numeric error-code events in process memory. For alpha2 speech errors, match the entire SDK-generated message against fixed known strings and record only the matching fixed error-type token; do not store the message itself. They never contain audio, transcript text, arbitrary exception messages or endpoints; they disappear when the process ends and are copied only on user action in Settings. Runtime `ErrorResponse` codes must not be discarded. A successful build or readiness status does not establish that device recognition works.

For explicitly authorized system-log diagnosis, bound the capture window and filter in memory to fixed allowlisted indicators without saving raw lines. An unmatched indicator does not rule out a cause.

At the live capture cap, stop/release the microphone, retain PCM and wait for explicit Stop/Cancel, with a cue; do not finalize or submit automatically. Trace the IPC deadline and client timeout when changing the cap. A notification shade or transient focus loss does not cancel capture, while screen-off/lock and local service teardown follow the local safety policy; they must not hijack external ownership.
